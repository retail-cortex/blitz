## 1. Purpose

An agent that can read the team's data answers questions no file in the repository can: how many orders failed last night, which customers churned, what the schema looks like before a migration. [MCP Toolbox for Databases](https://github.com/googleapis/mcp-toolbox) (Google, Apache-2.0, written in Go) already turns a database into MCP tools, with connection pooling, parameterised queries and a read-only model. Blitz runs it inside its own process, not as a program to install, and puts a form in front of it, so connecting a database is a few fields in Studio. Reading is the default, enforced by the database itself, so an agent can explore without the risk of changing anything.

## 2. Requirements

### Toolbox inside Blitz

- **DB-01** `third_party/mcp-toolbox` is a pruned copy of Toolbox (v1.14.0, `VERSION`): its core (`third_party/mcp-toolbox/internal/server`, its sources, tools and utilities), the PostgreSQL, AlloyDB, SQLite and BigQuery sources and their tools, and its config parser (`third_party/mcp-toolbox/embed/config.go`, from Toolbox's cmd/internal), under Blitz's module path so the embed package can import its internal packages. Toolbox's command line isn't used: its signal handling, its version check (a call home) and its global OpenTelemetry setup would act on Blitz's process. `tools/update_toolbox.sh [version]` refreshes the copy from the release's module and applies `patches/*.patch` in order; then `bazel run //:gazelle`. nogo skips `third_party/mcp-toolbox/internal` (upstream code).
- **DB-02** Blitz's patches: (01) SQLite through `ncruces/go-sqlite3` with **sqlite-vec** (`vec0` tables, nearest-neighbour queries; wazero with threads) and `readOnly` (the file opened `mode=ro`); (02) PostgreSQL and AlloyDB `readOnly`: every session `default_transaction_read_only=on`, and `execute_sql` runs in a read-only transaction rolled back after, so neither `BEGIN READ WRITE` nor `SET default_transaction_read_only = off` gets a write through; (03) no Cloud SQL; (04) `${NAME}` filled only from the values Blitz gives, never the process's environment; (05) the stdio server doesn't panic when its session closes; (06) closing the server closes its sources' pools and stops BigQuery's client caches (Toolbox never did, so each restart leaked connections).
- **DB-03** `embed.Load(files, values)` reads and merges Toolbox YAML files; `embed.Start` initialises the sources (connecting to each: a database that can't be reached is the error) and serves the tools as MCP over an in-memory pipe (`Session`, closed once). A custom SQL tool with no annotations whose statement only reads (`ReadsOnly`: it starts with SELECT, WITH, EXPLAIN, SHOW, PRAGMA, VALUES, DESCRIBE or TABLE and has no word that writes) is marked `readOnlyHint`, since Toolbox otherwise takes it for a write and hides it on a read-only source. `ReadOnlySources` and `ReadOnlyTools` name the sources that can't write (SQLite, PostgreSQL and AlloyDB with `readOnly`, BigQuery with `writeMode: blocked` or `readOnly`) and the tools on them.

### The databases server

- **DB-04** A workspace's **database files** are the global ones (`~/.blitz/connectors/databases/*.yaml`, `*.yml`) and its own (`.agents/connectors/databases/`), merged into one MCP server, **databases** (the category's `server`), run in-process by the toolbox backend (`MCPServerConfig.InProcess` `toolbox`, `tools.RegisterInProcess`): its tools are named `db__<tool>` and offered to every agent. A user's own MCP server named `databases` wins, with a warning. With no files there's no server.
- **DB-05** A `${NAME}` in a file is the Blitz secret `NAME` (the workspace's own, else the global one; spec_secrets_039), never an environment variable; its value is remembered for every redactor to mask. A workspace file the person hasn't trusted gets only the workspace's own (spec_connectors_047 CON-09).
- **DB-06** The server connects when its tools are first listed, like any MCP server (spec_mcp_009), and gives up after the listing's timeout; its state (idle, connected, failed with why) is in `/mcp` and Studio. Its target reads `in-process: <files>`.
- **DB-07** Tools on a read-only source run **without asking** (`MCPServerConfig.ReadOnlyTools`; `Lookup` reports them as auto-approved): the database refuses any write, whatever the agent sends. Every other database tool asks first, as MCP tools do, and so does every tool of a workspace file the person hasn't trusted (CON-09).
- **DB-08** The settings watch (every 2 s) notices database files added, changed or removed, and restarts the server (`ReloadConnectors`, CON-08); so does saving or deleting one in Studio. MCP reloads are applied one at a time (`applyMCP`, `mcpMu`).

### Connections in Studio

- **DB-09** A **connection** is one file, `<name>.yaml`: one source named `<name>` with the ready-made tools switched on (`<name>_execute_sql`, `<name>_list_tables`…) and the custom queries (`<name>_<query>`), so tool names never collide between files. `databases.Parse` reads a file into the form; one with more than the form describes (other sources or tool types, toolsets, unknown settings) is **custom**, listed and edited as YAML. A connection's description is kept in a `# about:` comment (Toolbox's sources take no description field) and goes into its tools' descriptions.
- **DB-10** The kinds (descriptors in `pkg/engine/connectors/builtin/kinds/`, spec_connectors_047 CON-01; each with every capability, and its schema read as CON-05 says): **PostgreSQL** (host, port, database, user, password; tools `execute_sql`, `list_tables`, `list_schemas`, `list_views`, `list_indexes`, `database_overview`); **AlloyDB** (project, region, cluster, instance, IP type, database, user and password or IAM; the PostgreSQL tools); **SQLite** (the file; `execute_sql`, which writes, and `list_tables`); **BigQuery** (project, location, datasets, most bytes billed; `execute_sql`, `list_datasets`, `list_tables`, `table_info`, `dataset_info`). Google Cloud kinds sign in with Application Default Credentials.
- **DB-11** A password is never in the file: saving keeps the value typed as the secret `DB_<NAME>_PASSWORD` (the category's `secretPrefix`, CON-07) in the connection's scope and writes `${DB_<NAME>_PASSWORD}`. A rename moves the secret; deleting a connection deletes its secrets. A required password with no value kept or typed is a problem.
- **DB-12** New connections are **read-only**. Custom queries take parameters (string, integer, float, boolean) and say whether they only read.
- **DB-13** The connector RPCs (spec_connectors_047 CON-10): `ListConnectors`, `SaveConnector` (`CONNECTOR_NOT_FOUND` for a previous name that isn't there), `DeleteConnector`, `TestConnector` (connects to the form as it is, unsaved, and lists its tools: which run unasked; a problem says why it couldn't connect, redacted), `TryConnectorTool` (runs one tool of the form as it is, with JSON arguments), `ReadConnectorSchema` and `DraftConnectorQuery`.
- **DB-14** **Studio › Connectors › Databases** (`ConnectorsPane`, spec_connectors_047 CON-11), after Workflows with Secrets (what the agent reaches; spec_studio_040 STU-02): the server's state, then the connections, this workspace's and every workspace's, each with its kind, where it is, read-only or not, its tool count and description. A connection's form slides in over the list: name and description, the folder it's kept in (Studio's are the workspace's; every workspace's are changed in Settings › Connectors, CON-18), the kind, its settings (a kept password shown as kept, typed to replace), **Read-only** with what it means for the kind, the ready-made tools (one that writes is marked as not offered while read-only), and **Your queries**, each with its SQL, parameters (drafted from `$1` or `@name` when the SQL is first written) and **Try it**, and **Write a query**, the query builder (CON-12). **Test the connection** lists the tools the agents would get. Delete, Revert, Cancel and Save as in the other kinds; unsaved changes are asked about.
- **DB-15** The strings are in English, Spanish and French.
- **DB-16** The leak checks of the test binaries that link Toolbox ignore opencensus's stats worker, which its package's `init` starts for the process.
- **DB-17** *2026-10-20 (the owner's question: can `./kitchen.db` work?).* A setting its kind marks as a path (`type: path`: SQLite's `database`) is kept in the file as written, so a committed file means the same on every machine, and resolved only when Blitz connects (`connectors.ResolvePath`; `databases/paths.go`, through `embed.LoadWith`, which gives each file's text to a rewrite before Toolbox parses it; `Serve` works out which settings are paths from the workspace's catalog, its own kinds too, and hands them to the transport as `MCPServerConfig.FileSettings`): a relative one against the workspace's folder for a workspace connection (`<workspace>/.agents/connectors/<category>/`), the home folder for a global one, `~/` as the home folder; `:memory:`, a `file:` URI and a `${NAME}` are left as they are. Studio's Test, Try it and Read the tables resolve it the same way, by the connection's scope. A path naming no file is the connection's problem (*no file at …*), read-only or not: SQLite would otherwise make an empty database where the service runs. Make global (spec_connectors_047 CON-19) writes a relative path as the full one it named, so it still names that file. Only the built-in format Studio writes (a `kind: source` document a source) is resolved; Toolbox's older nested format is read as it is.
- **DB-18** *2026-10-20 (a leak review).* Toolbox closes what it opened when a start fails part-way (patch 07: `InitializeConfigs` and `NewServer` close the sources open so far on any later error, a source's, a tool's or the server's; BigQuery closes its client and caches on its own early errors), so a failing Test or a reconnect with one database down doesn't leak the others' pools, files and goroutines. A SQLite query returns at most `MaxRows` (1000) rows, the last saying so (patch 08), rather than loading a whole table. The secret values typed into Studio's form, unsaved, are masked in what a test or try answers, not remembered for the process's life. The patches are listed in `third_party/mcp-toolbox/README.md`.
