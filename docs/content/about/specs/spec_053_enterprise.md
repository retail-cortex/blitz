## 1. Purpose

Companies want Blitz's agents with their own sign-in, their own approved models, rules every employee works under, workspaces they share, and jobs that run when a laptop is shut. That service is licensed and closed source, in its own repository (`blitz-enterprise`), and the customer runs it in their own Google Cloud project. This spec is the open-source half: the seams that service plugs into, and what the desktop app, the CLI and the tray do when they're pointed at one. Without an enterprise service set, nothing here changes how Blitz works.

The line: open source holds the interfaces, their open-source defaults and the clients; the enterprise repository holds the implementations (OIDC, RBAC, SCIM, licensing, the model gateway, the catalog's authoring, Git sync, sharing, cloud jobs, Terraform). Nothing public imports anything private.

## 2. The service, assembled from `pkg/`

- **EN-01** *Built.* The service's assembly is in `pkg/service` (moved from apps/service/internal/daemon and apps/service/internal/server): `service.Run(ctx, service.Options)` opens each workspace a client names and serves it; `pkg/service/server` has the Connect handlers; `pkg/service/servicetest` runs it in other packages' tests. `apps/service/main.go` is the flags and that call. Another Go module can't import internal/, so this is what lets the enterprise service reuse the whole service rather than copy it.
- **EN-02** `service.Options` takes the extension points, each an interface in `pkg/` with an open-source default that keeps today's behaviour. `Authenticator` and `Authorizer` are built (`pkg/service/network.go`, with EN-03); each of the others is added with the feature that first uses it, so none is an interface nothing calls:

  | Point | What it decides | Open-source default |
  |---|---|---|
  | `Authenticator` | who a request is from, from its credentials | the Unix socket's owner (only they can open it) |
  | `Authorizer` | whether that caller may do an action on a workspace or item | allow (one user) |
  | `Catalog` | the organization's agents, rules, skills, guardrails, MCP servers, connectors and policies (§5) | none |
  | `ModelRouter` | where a model's requests go and which models a caller may use, for the engine when it runs in the service (jobs, §6); clients reach the organization's models through its gateway (§4) | the person's own settings (`[llm.*]`) |
  | `JobRunner` | where a job runs (§6) | this service |
  | `Telemetry` | usage counts sent elsewhere | none |
  | `WorkspaceStore` | where a workspace's files come from and go back to: on the client, the sync of an organization's workspace with the service (its clone through `<url>/git/<handle>.git`); agents never run in the service's own pod, only in job pods (§6) | the local folder |

- **EN-03** *Built.* `service.Options.Network` serves the API on a second listener, beside the Unix socket, over TLS (HTTP/2, and HTTP/1.1; `server.ServeTLS`). It's used only when the program running the service sets it (blitzd never does), and it needs a listener, a certificate and an `Authenticator`. Every request on it needs credentials the `Authenticator` accepts, else `401` with `{"code": "unauthenticated", …}`, and the `Authorizer` (when given) must allow its procedure, else `403` with `forbidden`. The caller is in the request's context (`service.CallerFrom`). `Network.Routes` are the program's own paths on the same listener (discovery, health checks, its own sign-in): a request one of its patterns matches goes there without the `Authenticator`, the program checking its callers itself, and every other request is Blitz's, guarded. An `Authenticator` or `Authorizer` that returns a `service.Refusal` answers with its own status and code (`403 terms_required`, say). The socket serves its owner as before. `Network.Wrap` sees every request first, so a program's own session can stand in for the credentials `Auth` reads (the enterprise admin console's cookie, its spec_011_admin AD-11). `Network.Plain` serves without TLS instead (HTTP/1.1, and HTTP/2 in the clear; `server.ServePlain`), for a platform that ends TLS in front of the program and forwards over its own network: Cloud Run's front end, say. Plain needs no certificate; everything else is the same.
- **EN-04** *Built.* `//tools:check_deps` checks that nothing in this repository imports `github.com/retail-cortex/blitz-enterprise`, and that the CLI, the tray and the Electron app's tools don't reach `pkg/service`.
- **EN-05** *Built* (2026-11-01; `pkg/webui`, `@blitz/webui`: `bazel test //pkg/webui:all`). **The page's controls as a package:** the desktop page's controls (`src/ui`: Button, IconButton, Tabs, Segmented, MultiSelect, Menu, Dialog, Snackbar, Switch, Field, Drawer, the charts), its styles and themes (`m3.css`, `glass.css`, `themes.css`, the palettes) move to `pkg/webui`, a TypeScript package (pnpm's `workspace:*`, linked by Bazel as `//pkg/webui:pkg`; its words come from the app's translator, `setTranslator`) the desktop page imports, so another program's web pages look like Blitz without copying it: the enterprise admin console (its spec_011_admin) builds on it from Blitz's Bazel module. It holds no Blitz-specific state or API calls. New shared controls (a data table, a diff viewer, a date range) are added there.

## 3. Connecting to an organization's service

- **EN-10** *Built (2026-11-01; `pkg/config` `[enterprise] url`, `config.SetEnterpriseURL`; machine-wide 2026-11-02: `managed.toml` in `/Library/Application Support/Blitz` on macOS, `%ProgramData%\Blitz` on Windows, `/etc/blitz` elsewhere, or `BLITZ_MANAGED_SETTINGS`, with `[enterprise] url` and `workspaces_dir` over the person's; while it sets the address, blitzd refuses to change it (`MANAGED`), and Settings › Organization and `blitz enterprise status` say it's device management's).* `[enterprise]` in the settings: `url` (the service's address). Set by the person (Settings › **Organization**, `blitz enterprise connect <url>`) or by the company's device management in the machine-wide settings; a workspace's settings can't set it.
- **EN-11** *Built (`pkg/enterprise`, its `Discover`).* Discovery: `GET <url>/api/v1/info` gives the service's name, version, its OIDC issuer and client ID, the token lifetime, and its capabilities (`models`, `catalog`, `jobs`, `sharing`, `workspaces`, `branding`). Clients show only what's listed.
- **EN-12** *Built (`pkg/enterprise`; blitzd's `ConfigService.EnterpriseSignIn`, `blitz enterprise login`, Settings › Organization; since 2026-11-03 the browser ends on a card on Blitz's glass (`pkg/signedin`, also `blitz mcp login`'s) saying whether it worked, with **Open Blitz**, a `blitz://show` link that brings the window forward; in the organization's branding when Blitz keeps one (EN-50): its logo for each theme, else its name, its accent on the button, and a small "Blitz" below).* A provider that needs a client for each kind of app (Google) has the service name them in `/api/v1/info` (`oidc.desktop`, `oidc.device`, each with its non-confidential secret); one client serves all when it doesn't. Blitz renews with the latest refresh token kept, read just before, so a CLI and the service on one computer don't spend each other's. Sign-in goes straight to the company's identity provider: the desktop app and the tray with authorization code and PKCE on a loopback redirect, the CLI with the device-code flow (`blitz enterprise login`). The refresh token is kept in the keychain (spec_039_secrets); the access token in memory. A token is renewed before it expires (the service sets how often, in hours); a refused renewal signs the person out and says so. The calls are JSON over HTTPS, so open-source clients need nothing from the service's code:
  - `POST <url>/api/v1/session` with `{"id_token", "client"}` (the provider's ID token, and the client and its version) answers `{"access_token", "refresh_token", "expires_in", "person": {"id", "email", "name", "roles"}, "terms": {"version"}}`; `terms` is there when there's a version to accept (EN-53).
  - `POST <url>/api/v1/session/refresh` with `{"refresh_token"}` answers the same, with a new refresh token: the old one ends the session if it's used again, so a client renews one at a time and keeps the new one before it uses it.
  - `DELETE <url>/api/v1/session` signs this session out; `GET <url>/api/v1/sessions` lists the person's sessions; `POST <url>/api/v1/sessions/end-others` signs the others out.
  - Every other request carries `Authorization: Bearer <access token>`.
  - Refusals are `{"code", "message"}`, the message written for the person: `401 unauthenticated` (sign in again), `403 forbidden`, `403 license_lapsed` (no new sign-ins), `403 terms_required` (EN-53).
- **EN-13** *Built (2026-11-02): a banner in the window, checked at start, every 2 minutes and when the settings change, with Sign in (Settings › Organization) or Retry, and the model's error, which says to sign in.* Signed out, or the service unreachable: the window says which, with **Sign in** or **Retry**. Work that needs the service (its models, cloud jobs, shared workspaces) waits; local workspaces work as before, under the last catalog (EN-33).
- **EN-14** *Built (`blitz doctor`'s organization line, `blitz enterprise status`).* `blitz doctor` shows the service, whether it's reached, who is signed in and when the token renews.

## 4. The organization's models

- **EN-20** *Built (`runtime` provider `enterprise`), but for the catalog's policy letting personal providers in, which comes with §5: connected, the organization's models are the only ones.* With `models` listed, the service is the model provider: the `api` provider (`[llm.api]`) is filled from the service (its base URL), with the access token in place of a token script, and the person's own providers are off unless the catalog's policy allows them.
- **EN-21** *Built (2026-11-02) for IDs, display names, the default, prices and capabilities, with the ETag: Settings › Providers shows the organization as the one provider, its models to choose the default from (`enterprise/<model>`) and, under the choice, what that model can do and its price; `blitz models` lists each with its name, the default and what it can do. The capabilities are `tools`, `images`, `thinking` (true or false) and `context` (tokens), set in the admin console's model form; Blitz shows them, and doesn't yet hold back what a model can't take.* The model menu lists `GET <url>/api/v1/models` (sent with `If-None-Match`): each model's ID, display name, vendor, the API it speaks (Anthropic's Messages or OpenAI's Responses; the service translates for the models that speak neither), capabilities (tools, images, thinking, context size), price per million tokens and whether it's the default. The list is the caller's: the service filters it by role.
- **EN-22** *Built (2026-11-02): `Blitz-Workspace` is the service's ID for the workspace, found as it opens by matching its folder to the organization's workspaces (a clone, or a folder shared in place); a workspace that isn't the organization's sends none.* Every model request carries `Blitz-Workspace`, `Blitz-Session` and `Blitz-Agent`, so the service applies the workspace's and the agent's guardrails to it.
- **EN-23** *Built* (`pkg/guardrails`, a public package over the engine's private `pkg/engine/gates`). The guardrail checks the service runs on model traffic are the ones this repository runs (`pkg/engine/gates`: `RedactInjection`, `ConfirmInjection`, `CommandDenied`, `DomainAllowed`, the secret scan, the limits), exported for a caller that has a model's request and reply rather than an engine turn, so a rule means the same at the service as on the desktop.
- **EN-24** *Built (2026-11-02): **Your usage** in Settings › Providers & keys under the organization's models, and `blitz enterprise usage` (blitzd's `GetOrgUsage`); a request refused for a budget or quota says the gateway's own words (whose limit, what's left, when it resets) and where to see the rest, never HTTP 429 (`runtime.ErrOrgLimit`). A rate-limited request is retried by the model's own client after `Retry-After`, up to `max_retries`, with **Waiting for <model>: busy. Trying again in Ns…** in the window and the terminal while it waits (any provider's 429, 503 or 529; the model from Gemini's path or the request's `model`).* **Your usage and limits.** Settings › Models shows the person's own usage of the organization's models this day and month, by model (tokens and cost), with each budget and token quota that applies and what's left (`GET <url>/api/v1/usage`, the enterprise spec's GW-27). A request refused for a budget or quota (`budget_exceeded`, `quota_exceeded`) is shown as that, never as a model failure: which limit, what's left, when it resets, and the other models the person may still use. A request refused for a rate limit (`rate_limited`, GW-15) is sent again after its `Retry-After`, with **Waiting for <model>: busy** in the window, for up to 2 minutes before it's shown as an error. While the organization keeps full prompt logs that include the person (the enterprise spec's GW-21), Settings › Models says *"Your organization keeps what's sent to its models"*, from `/api/v1/usage`.

## 5. The organization's catalog

- **EN-30** *Built (2026-11-02): checking in `pkg/catalog`, for the service's builds; the clients' side in `pkg/enterprise` (its `RefreshCatalog`), blitzd's catalog loop and `pkg/config`'s organization layer. Agents, skills, rules, guardrails, commands, MCP servers and connections apply (connections 2026-11-02: the catalog's `connectors/<category>/<name>.yaml` are the `org-locked` and `org-default` scopes beside global and workspace; a locked one takes the place of the person's of its name and can't be turned off, a default gives way to a person's that's used; they're trusted, take the person's global secrets, show in Studio's Connectors as the organization's and don't open there; `blitz enterprise catalog --kind connector` lists them).* With `catalog` listed, the organization's agents, rules, skills, guardrails, MCP server and connector definitions (never their secrets), slash commands and policies come from the service, as a signed bundle with a version.
- **EN-31** *Built: the catalog's files are laid out in `~/.blitz/enterprise/<host>/catalog/default` and `…/locked`, each as an `.agents` folder; defaults load before the person's and the workspace's (which win) and locked items after (which win over them), for agents, skills and commands; for rules and guardrails, where the first folder wins, the other way round; an MCP server locked replaces the person's of its name, a default one is added unless they have one. The policy's `[builtins] off` switches off Blitz's built-in agents, skills and guardrails by name (2026-11-02), but the agent sessions start with, which is kept with a warning; a switched-off agent's name stays reserved.* A layer above the workspace's and the person's: an organization item is **locked** (it applies and can't be changed or switched off) or a **default** (a workspace or the person may override it). The policy may switch off Blitz's built-in items.
- **EN-32** *Built: blitzd fetches it once signed in (each file by its SHA-256, checked, kept across versions), follows the stream, fetching again for each version it announces, and fetches on the policy's `refresh` while the stream is down.* Delivery (the service's side is the enterprise spec's: `GET <url>/api/v1/catalog`, signed with a key `/api/v1/info` lists as `catalog_keys`; its files at `/api/v1/catalog/files/<sha256>`; the stream at `/api/v1/catalog/watch`, server-sent events): a stream from the service sends a new bundle as soon as it's published; when the stream isn't up (at start, after a reconnect), the bundle is fetched with `If-None-Match`, and again after its `Cache-Control: max-age`. A bundle whose signature doesn't check against the service's key is refused and the last one kept.
- **EN-33** *Built: the manifest is kept signed beside its layers and checked again when read; past its expiry the organization's models wait (`your organization's catalog is out of date`).* The last good bundle is kept on disk (EN-54) with its expiry. Out of date past the expiry, organization workspaces stop until the bundle is fetched again; Blitz never falls back to working without the organization's rules. The branding doesn't expire with it (EN-54).
- **EN-34** *Built (2026-11-02): the window's agent menu marks the organization's agents (`AgentInfo.org_lock`); Studio's Agents, Skills, Rules and Guardrails lists end with **From your organization**: each item with its lock and groups, a locked one saying its Admins change it through a review, a default one with **Copy to this workspace** (and, once copied, saying the workspace's own takes its place); `blitz enterprise catalog [--kind]` and `blitz enterprise catalog copy <kind>/<name>` (commands and connectors too); blitzd's `ListOrgItems` and `CopyOrgItem`.* Studio and Settings show organization items with a badge and their lock; locked ones can't be edited, only copied into the workspace when they're defaults.
- **EN-36** *Built (2026-11-02): Studio's header button **Publish to organization…** for the organization's Admins (the workspace's .agents items, each with its lock and groups and what the catalog would refuse, sent as one review, and the catalog's reviews with their state), `blitz enterprise publish [<kind>/<name>…]` and `blitz enterprise reviews`; blitzd's `ListPublishable`, `PublishToOrganization`, `ListCatalogReviews`; `catalog.Place` sets lock and groups in the published copy (the workspace's own file is unchanged). An Admin (its author too) approves in the admin console's **Catalog › Reviews**.* **Publish to organization** in Studio, for a signed-in Admin: from an item's menu, or several chosen in the list, with each one's lock (`locked` or `default`) and groups. Blitz sends them to the service as a review (the enterprise spec's CA-04) and shows its state on the items (**In review**, with its problems if the checks found any, then **Published** with the version); an Admin, its author too, approves it in the admin pages. Locked organization items show who may change them (Admins, through a review) instead of an edit button.
- **EN-37** *Built (2026-11-04; `pkg/enterprise` `reach.go`).* **When the service doesn't answer.** Blitz works on as if offline, signed in or not: workspaces open and their files, the editor, Git and the terminal work; the organization's models (so the agent) wait, the conversation saying the organization can't be reached. A service that takes a request and never answers is given up on: connecting (10 s), its TLS handshake (10 s), the wait for its answer to start (20 s; a stream's or a download's body takes as long as it takes), the organization's models as a workspace opens (8 s), the workspace's ID (5 s); and once it hasn't answered, calls to it fail at once for 30 s instead of each waiting again (an answer clears that; a caller giving up doesn't count). An organization workspace keeps what the service last said of it while it doesn't answer: its ID, and a Viewer's clone stays read-only. While a workspace opens, the Files view says so (after 0.3 s, a spinner and **Opening the workspace…**), and after 1.5 s what it's waiting for: **Waiting for <the organization>: the workspace opens without it in a moment**; never an empty list that isn't.
- **EN-35** *Built for the person's own providers (allowed: a model named with their provider uses it, bare names stay the organization's), MCP servers (not allowed: theirs are dropped), connections (`[connectors] own` and `kinds`: the person's not allowed, or of a kind not listed, are listed with why and not served, and can't be saved), `!` commands, and tools (denied for every agent).* The policy may also: allow or forbid the person's own providers, MCP servers and connectors; switch off `!` commands or named tools; set guardrails no workspace can loosen.

## 6. Jobs on the service

- **EN-40** *Built (2026-11-02; `pkg/jobspec`, which the service reads jobs with too; the local scheduler skips `service` jobs; Studio keeps it through an edit). Studio's **Runs on** and **Move to the service** (with what wouldn't work there), and `blitz jobs move <name> [--anyway]`; a run on the service is `service.RunJob` (blitz-enterprise's `blitz-runner`, or `blitzd run-job`), which works in its own folder, `jobs/<person-id>/<job-id>/<run-id>/` (the clone in `workspace/`, what it leaves for people in `out/`), clones the workspace with its run's token, runs the job as its owner, pushes its changes to the run's own branch `blitz/jobs/<job>/<run-id>`, keeps `out/` and its log (`events.jsonl`) as the run's artifacts (spec_055_urns), and reports its end.* A job has `runs_on`: `here` (the default, today's) or `service`, and **Runs on** in Studio › Jobs with **Move to the service**. One job runs in one place; there is no "here when on, the service otherwise".
- **EN-41** *Built (2026-11-02; `engine.Workspace.ServiceProblems`, `MoveToService`; WorkerService `MoveWorkerToService`): Studio's **Move to the service** and `blitz jobs move <name>` say what won't work there (an MCP server that's a program here or at a local address, a connector reaching this computer, a file outside the workspace the job names, a `localhost` address in it) and move only when nothing does, or **Move anyway** (`--anyway`). Studio's job form shows **Runs on** and **When it needs more** in an organization workspace and keeps both through every edit (before, an edit in Studio dropped `runs_on`).* Before a job moves, Blitz checks it can run there and says what can't: an MCP server that runs only on this computer (stdio), a file outside the workspace, a `localhost` address, a connector the service doesn't have.
- **EN-42** *Built in Studio › Jobs (2026-11-02): a job with `runs_on: service` in an organization workspace shows the service's runs of it in place of this computer's (status, how it started, its last message, cost, its branch, and its files on request, each saved to Downloads), with **Run now** and **Turn on/off** there (ConfigService `GetServiceJob`, `RunServiceJob`, `SetServiceJobEnabled`, `ListServiceRunFiles`, `SaveServiceRunFile`; refreshed as the service's stream says a run of it changed). A job the service hasn't got says why, with what to do (2026-11-02, the owner: the old note had no action): its WORKER.md isn't in `.agents/workers/<name>/`; its changes aren't on main (**Push to main**: blitzd's `PushServiceJob` commits the job's folder, pushes the workspace to main and has the service read it; `blitz enterprise jobs push <job>`); sync is putting them there (with sync's state, looked at again until it's done); or main has it and the service doesn't run it (the service's why). Each look has the service read main at once (`POST /api/v1/workspaces/{handle}/jobs/read`), so a service that scales to zero doesn't keep it waiting. The runs going now on the service show in the status bar's Processes menu and the Processes view under **On your organization's service**, one picked opening its job in Studio (`WatchServiceRuns`, over the service's `GET /api/v1/runs/watch`; nothing is polled).* A service job's runs show beside local ones in Studio › Jobs and the Processes view, with their output, from the service (`JobRunner`); the person's computer doesn't need to be on for them to run.

- **EN-44** *Built (2026-11-03): a run's changes reach main (blitz-enterprise spec_009_jobs JB-10): the runner adds a succeeded run's branch to main as WORKER.md's `merge` says (`main`, the default, when they merge cleanly; `never`), through `pkg/runmerge` (fetch, merge, push, again when main moved), and says whether they're on main and why not (`merged`, `merge_note`). Studio › Jobs shows a run's changes on main, or its branch and why with **Add to my workspace**; `blitz enterprise jobs take <job> [run]`. Both are blitzd's `TakeServiceRun`: the merge in a clone of its own (never the folder's files; `CONFLICTS`, `NO_CHANGES`, `UNKNOWN_RUN`), then the service told (`POST /api/v1/jobs/{id}/runs/{run}/merged`, an Editor) and the folder's sync fetching it.* A job run on the service never leaves work where nobody finds it.
- **EN-43** *Built (2026-11-02): `on_request` in WORKER.md (refuse or pause; unset, pause on the service); the runner pauses at the first request its permissions don't allow, pushes its branch, keeps its session among its files and reports `paused` with the request; answered, the service starts the same run again, which restores its session and branch and goes on with the answer as its next message, the approved request allowed once (`engine.RunOptions` `OnRequest`, `Session`, `Prompt`). The status bar's **waiting for your answer** item (with a notification for each new one) and Studio › Jobs show and answer them, as `blitz enterprise jobs pending|approve|deny` does; blitzd's `ListServiceApprovals`, `AnswerServiceRun`; the tray's **Jobs: N waiting for your answer** menu, each run with what it asks, **Approve**, **Deny** and **Show in Blitz**; email and webhook notices (the enterprise spec's JB-31) set in Settings › Organization's **Job notices** and `blitz enterprise notices` (blitzd's `GetOrgNotices`, `SetOrgNotices`).* A job's `on_request` says what a run does when it needs something its permissions don't allow: `refuse` (today's, WK-42; the default for jobs here) or `pause` (the default on the service). A paused run is saved, not kept running: its session with the waiting request, and its changes on its branch. Its process ends. The owner sees the request (a notification, the Jobs view, the tray's Jobs menu, `blitz jobs pending`) with **Approve** or **Deny**, whenever they get to it. The answer resumes the run from where it stopped, with the decision as the tool's result. Background processes the run had started don't come back. A run waiting longer than `approval_wait` (7 days by default) stops. While a run waits, the job's next times are skipped, as `overlap: skip` skips them while a run goes on.

## 7. Branding and terms

- **EN-50** *Built (2026-11-02; `pkg/enterprise`, its `RefreshBranding`; blitzd's `GetBranding`). The envelope is `{"kid", "payload", "signature"}`: the payload's JSON in base64url, and an Ed25519 signature, base64url, of `blitz-enterprise/v1`, NUL, the key ID, NUL and the payload, checked against `/api/v1/info`'s `catalog_keys` (base64), asked again once for a key published since. The desktop app asks for it at start, every 10 minutes and when the settings change.* With `branding` listed, `GET <url>/api/v1/branding` (with `If-None-Match`) gives:
  - the app's name and short name;
  - a logo and an icon, each for light and dark;
  - two accent colours, one for the light theme and one for the dark (no one colour reads well on both);
  - a support link and an about text;
  - the terms of service and privacy notice, each as text or a link, with a version.

  It needs no sign-in, so the sign-in screen is branded too. It comes signed with the catalog bundle's key (EN-32), the images inside it rather than linked, so one signature covers everything the window shows and an offline start has all of it. A copy whose signature doesn't check is refused and the last one kept. It's kept on disk (EN-54), so the window is branded before it reaches the service.
- **EN-51** *Built (2026-11-02): the window's title, the top bar (the short name, the logo for the theme), the welcome page and the accents (checked at 4.5:1 against each theme's background); every word the window, the tray, the CLI and blitzd's notifications say through their translations (`setAppName` in the page's `i18n.ts`, `i18n.SetAppName` in Go, the organization's name in place of "Blitz"), but for the keys that name the program itself (its releases, license, themes, reinstall hints and "Built on Blitz": `fixedKeys`, the same in both); the CLI's banner and title. The tray and the CLI read the kept branding when they start.* The name replaces "Blitz" wherever the app says it at run time:
  - the window's title;
  - the page's menus, the welcome page and dialogs;
  - notifications;
  - the tray's tooltip and menu titles;
  - the CLI's banner and help.

  The logo replaces the mark in the title bar and on the welcome page. Each accent replaces its theme's accent tokens, and is refused, keeping Blitz's, when it doesn't meet WCAG AA contrast (4.5:1) against that theme's background. What the system names from the app's bundle can't change at run time: the macOS Dock and menu bar, the installer, the Start menu and file names. Those need a rebranded build, which is out of scope here.
- **EN-52** *Built in the desktop app.* **About** shows the organization's name, logo, about text, terms of service, privacy notice and support link. It always ends with "Built on Blitz <version>", plus Blitz's license and notices (the Apache License's NOTICE must stay with the program).
- **EN-53** *Built in the desktop app (a dialog before anything else, checked at start, every 10 minutes and when the settings change; Decline signs out) and blitzd (`GetTerms`, `AcceptTerms`); and the CLI (`blitz enterprise login` asks `[y/N]` when a version waits, `blitz enterprise terms` any time).* **The user agreement:** after sign-in, and whenever the terms' version changes, the window shows the terms with **Accept** and **Decline** before anything else. The CLI shows them, or their link, and asks `[y/N]`. Accept is recorded on the service with the version and the time (`POST <url>/api/v1/terms/accept` with `{"version"}`; `GET <url>/api/v1/terms` is the version in force and whether it's accepted). Decline signs out. Until the current version is accepted, the service answers every other request with `403 terms_required`, so no client can skip it.
- **EN-54** *Built for the branding: kept in `~/.blitz/enterprise/<host>/` with the keys it was checked with, read back and checked again offline, removed on disconnecting or moving to another organization.* **Offline** *(the owner's question, 2026-10-29: "how it will be persisted when the user is offline")*:
  - **Where.** The last good bundle and branding, each as the signed copy the service sent, are kept in the service's own folder, `~/.blitz/enterprise/<the service's host>/` (0700, files 0600, each written to a temporary file and renamed into place), so another service's never mixes in. At start the window reads the branding from there and checks its signature again before it shows it; a copy that doesn't check is ignored (Blitz's own look until the service answers).
  - **No expiry.** The branding is how the app looks, not a rule, so it stays until a newer one replaces it. Past the bundle's expiry (EN-33) the organization's workspaces stop, but the window keeps the organization's name and logo. A service that stops listing `branding` returns the app to Blitz's.
  - **Signed out.** Signing out, or a token that can't be renewed, keeps the branding and the terms: it's still the organization's computer, and the sign-in screen (EN-13) wears its name.
  - **Disconnected.** Removing `[enterprise] url` (Settings › **Organization**, `blitz enterprise disconnect`, or device management) deletes the folder, and the app is Blitz again.
  - **The terms.** Their text and version are kept with the branding, so About shows them offline. Acceptance is recorded only on the service (EN-53). Offline, the version last accepted on this computer stands, and a newer one is asked for, before anything else, when the service answers again.

## 8. Organization workspaces

*Draft* (2026-11-01). The client's `WorkspaceStore` (EN-02): an organization's workspaces are Git repositories kept by the service (the enterprise spec's spec_007_workspaces), cloned to the person's disk, where Blitz's agents work as they do in any folder.

- **EN-60** *Built (2026-11-02; Create in the window, **New workspace…** with **Just for me** for a personal one, and the Viewer's read-only clone, `Tools.ReadOnly` set by blitzd as the workspace opens, added later that day): the Workspaces menu lists them under the organization's name, `blitz enterprise workspaces`, `open <handle>` and `create <name>`; blitzd's `ListOrgWorkspaces`, `OpenOrgWorkspace` (cloning with only Blitz's helper, never asking at a terminal) and `CreateOrgWorkspace`; `[enterprise] workspaces_dir`.* **Open an organization workspace.** Signed in, the window's workspace picker and `blitz workspaces` list the workspaces the person has a role in (`GET <url>/api/v1/workspaces`), under the organization's name, with **Create a workspace**. Opening one the first time clones it through the service (`<url>/git/<handle>.git`) to `[enterprise] workspaces_dir` (`~/Blitz/<organization>/` by default) and opens it; after that it opens the clone. The clone is made beside that folder and moved into place whole, so its sync never finds one half made, and a folder of the person's own files already there is left as it is (`FOLDER_IN_THE_WAY`: move them, then open it again). A Viewer's clone is read-only: Blitz's file tools and the editor refuse to change it, saying why.
- **EN-61** *Built (`pkg/gitcred`): the clone's settings name `blitzd git-credential`, which asks the running service (`GitCredential`), the one process that renews the token; `blitz git-credential` does the same for Git's own settings.* **The credential helper** `blitz git-credential` (Git's credential protocol: `get`, `store`, `erase`). Blitz sets it in each organization clone's own Git config (`credential.<url>.helper`), never the person's global config. `get` answers the service's host with the access token from the keychain (spec_039_secrets), renewed first when it's within its last minute (EN-12); signed out, it answers nothing, so Git fails with "sign in to Blitz", and Blitz says so. A person may set it globally to use Git's own clients with the service. Changes' Pull and Push accept this one setting in a folder's own config, exactly as Blitz writes it (DSK-90b), and each sync start rewrites it with the running Blitz's path.
- **EN-62** *Built (2026-11-02; `pkg/orgsync`, blitzd's sync manager): for each cloned workspace with sync on (not a Viewer's), while signed in. Changes are found by `git status` every 2 seconds rather than a file watcher; others' changes are merged rather than rebased onto (the person never sees the history's shape, and keeping both versions is simpler and safer mid-merge), after this person's edits are committed. Its stream is followed, with a fetch each minute besides.* **Sync** (for a workspace with `sync` on; the enterprise spec's WS-04). Blitz's service, not the window, runs it, so it goes on with the window closed:
  - **Saving:** a change on disk (the person's, or an agent's write) starts a timer; 5 seconds after the last change, and never while an agent's turn in that workspace is still writing, Blitz commits everything (`git add -A`, its ignore rules included) with a message that says who changed what (*"Ana: edited plan.md"*, *"Coder (Ana's session): 4 files"*) and pushes.
  - **Getting others' changes:** Blitz fetches when the workspace opens, when the watch stream (WS-06) names a commit it doesn't have, and before each push. It rebases its own commits onto what it fetched. Changes from others land between turns: while a turn runs in the workspace, they wait for it to end, so an agent never has a file change under it mid-turn.
  - **A push refused** as not a fast-forward is fetched, rebased and tried again, up to 3 times, then retried as the watch stream brings news.
- **EN-63** *Built, the agent's next turn told of each pair once (2026-11-02: blitzd adds a `<workspace-sync>` note to the turn's prompt, the transcript keeping what the person wrote); the window's **2 files have both versions** is the status bar's, with each pair in its hover.* **Conflicts.** When a rebase can't apply a change to a file, Blitz keeps both: the other person's version under the file's name, and this person's beside it as `name (conflict, Ana).ext`, committed and pushed like any change. The window shows **2 files have both versions** with each pair, and the agent's next turn is told of them. A file deleted by one and changed by the other keeps the changed one. Nothing is ever lost: the person's own commits stay in the clone's reflog.
- **EN-64** *Built (2026-11-02): the status bar, whose menu has **Save now** (`SaveOrgSync`: commit, take others' changes and push at once, the state after; `NOT_SYNCED`, `GIT_BUSY` while a turn runs) with why it isn't saved, and `blitz enterprise sync` (`sync status` to only look) (in place of Git's item for a sync workspace in simple mode, beside it in advanced mode; `GetOrgSync`), and a sync workspace's Changes menu: **Session** and **Workspace history…** (each save with who and when, opened or restored, which sync saves as a new save), in simple mode too, and Git's items (Git view, Include all, Commit) only in advanced mode (the owner, who lost them on a folder shared in place). A push the service reached and turned down is **Not saved: the service refused it**, Git's reason in its tooltip and in blitzd's log (`orgsync.Refused`; `GetOrgSync`'s `error`), never Offline.* **The state is always shown, never in Git's words.** The status bar shows the workspace's sync state: **Saved**, **Saving…**, **Offline: saved on this computer** (commits wait and go when the service is back), **Signed out: sign in to sync**, or **Both versions kept** (EN-63). The window never says commit, push, pull or rebase for a sync workspace; its Changes view shows **History** instead, each save with who and when, and any one can be opened or restored as a new save.
- **EN-65** *Built for the clones; the watch stream's **New changes on main** comes with EN-62.* **Workspaces without sync** (code, the default for repositories with a build file) are plain clones: Blitz's Git features work as with any repository (Changes, branches, merges, worktrees), with the credential helper, and the watch stream only shows **New changes on main** in the window.
- **EN-66** *Built (2026-11-02; the owner asked how an existing workspace can sync): **Share <folder> with <organization>…** in the Workspaces menu, `blitz enterprise share`, blitzd's `ShareWithOrganization`, `~/.blitz/org-folders.json`.* **Share a folder where it is.** A folder already on this computer becomes an organization workspace (a team's, or the person's own) without moving: its changes are committed first (said so), the folder and its whole history are checked for secrets (`pkg/secretscan`; nothing is made or sent when any are found, each named by file and line), files over 50 MB are mentioned, the workspace is made, and the folder is pushed to its `main` through a remote of its own, `organization`, so a repository's `origin` stays as it was; its branch follows `organization/main` when it followed nothing (so Changes can pull and count; a folder shared before 2026-11-02 gets it as its sync starts). From then on it's kept in step where it is, as any clone is (EN-62), and listed where it is. A folder inside another repository is refused (its repository's folder is shared instead), as is one that's the organization's already.

## 9. Not in scope

- The enterprise service itself: OIDC, roles and SCIM, licensing and the heartbeat, the gateway, the catalog's authoring (policy as code), Git sync, sharing, cloud jobs, the database and Terraform. Those are specified in `blitz-enterprise`.
- Making the person's own computer enforce the organization's rules against the person: a local agent runs under rules it fetched (EN-33), which is best effort; what a company must be sure of goes through the service (its models, its data, its jobs).
